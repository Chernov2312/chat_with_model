# API и состояние бэкенда

Документ отражает текущий исходный код, а не гарантирует, что все операции уже
работают сквозным образом.

## Модели данных

В проекте остаются четыре ORM-модели: `User`, `Model`, `Session`, `Message`.
Таблица и модель `Generation` удалены.

- `User`: username, email, хеш пароля.
- `Model`: провайдер, отображаемое имя, размер контекста и поддержка streaming.
- `Session`: обязательный `model_id`, опциональный `user_id`, настройки генерации,
  опциональное название и архивный статус.
- `Message`: сессия, роль, содержимое и опциональное число токенов.
- `User.sessions` и `Session.user` связаны через SQLAlchemy `relationship`;
  связь двусторонняя (`back_populates`). `user_id` пока допускает `NULL`, поэтому
  старые и анонимные сессии могут не принадлежать пользователю.

`Base.metadata.create_all()` создаёт отсутствующие таблицы, но не изменяет
существующие. Для добавления `sessions.user_id` в уже созданную БД требуется
миграция (например, Alembic), а не только перезапуск приложения.

## Маршруты по исходникам

Основное приложение подключает роутеры; `/health` объявлен без префикса.
Обработчик `lifespan` с `create_tables()` определён, но не передан в `FastAPI`,
так что автоматическое создание таблиц при старте не включено.

| Метод | Путь в приложении | Назначение | Текущее ограничение |
|---|---|---|---|
| `GET` | `/health` | Проверка состояния | Возвращает `{"status":"healthy"}` |
| `POST` | `/api/v1/sessions` | Создать сессию | Схема присылает имя модели, а ORM требует `model_id`; user не назначается |
| `GET` | `/api/v1/sessions/{session_id}` | Получить сессию | Ответ DAO и схема истории не согласованы |
| `GET` | `/api/v1/sessions/{session_id}` | Удалить сессию | Декоратор удаления ошибочно объявлен как `GET`, конфликтует с чтением |
| `POST` | `/api/v1/sessions/{session_id}/messages/stream` | SSE-генерация | Контракт и сохранение истории не согласованы с моделью Message |
| `POST` | `/api/v1/api/v1/auth/register` | Регистрация | Повторный `/api/v1` из router-prefix и include-prefix |
| `POST` | `/api/v1/api/v1/auth/login` | Вход | Повторный `/api/v1` из router-prefix и include-prefix |
| `GET`, `PATCH` | `/api/v1/api/v1/users/me` | Профиль | Повторный `/api/v1` из router-prefix и include-prefix |

Маршрута `GET /sessions` или эквивалентного ему списка сессий сейчас нет.
Также нет API каталога моделей.

## Что нужно реализовать для списка чатов

1. Добавить авторизацию и владение сессией: создание сессии должно сохранять
   `user_id` из проверенного access token; операции чтения, изменения, удаления
   и отправки сообщений должны проверять владельца. Не принимать `user_id` от
   клиента как источник авторизации.
2. Решить судьбу анонимных сессий. Если список предназначен только для аккаунтов,
   сделать `sessions.user_id` обязательным после backfill/удаления анонимных
   строк и добавить FK-миграцию с индексом. Сейчас колонка nullable ради
   совместимости.
3. Реализовать `GET /api/v1/sessions` для текущего пользователя: сортировка
   по `updated_at` (сначала недавние), пагинация/лимит, исключение архивных по
   умолчанию. Элемент списка должен содержать как минимум `id`, `title`,
   `updated_at`, модель и превью последнего сообщения.
4. Добавить получение полной истории сессии (или включать историю в
   `GET /api/v1/sessions/{id}`) с упорядочиванием сообщений по `created_at`,
   проверкой владельца и ограничением/пагинацией для длинной истории.
5. Задать способ именования чата: пользовательское переименование и/или
   автогенерация `title` по первому сообщению; обновлять `updated_at` при каждом
   сообщении. Сейчас поле `title` есть в ORM, но соответствующие схемы и
   endpoints не реализованы.
6. Исправить создание сессии: сопоставить вход модели с `model_id` и заполнить
   связанные данные. Добавить тесты на изоляцию пользователей, пустые/длинные
   истории, пагинацию, удаление и недоступный чужой ID.
7. Согласовать пути регистрации/профиля, метод удаления и подключения
   `lifespan`; использовать миграции для обновления существующей схемы.

Фронтенд сейчас не показывает UUID и позволяет создать чат, но списка и выбора
ранее созданных чатов до реализации перечисленных API не будет.
